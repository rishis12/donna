# Git Branching Strategy

## Branch Structure

### `master` (Production)
- **Purpose**: Production-ready code
- **Deployment**: Auto-deploys to production environment
- **Protection**: Should be protected, requires PR reviews
- **Workflow**: Only merges from `staging` branch

### `staging` (Pre-Production)
- **Purpose**: Pre-production testing and validation
- **Deployment**: Deploys to staging environment
- **Workflow**: Merges from `develop`, tested before promoting to `master`

### `develop` (Development)
- **Purpose**: Active development branch
- **Deployment**: Optional dev environment
- **Workflow**: All feature branches merge here first

## Typical Workflow

```
1. Create feature branch from develop
   git checkout develop
   git pull
   git checkout -b feature/my-feature

2. Develop and commit
   git add .
   git commit -m "Add feature"
   git push -u origin feature/my-feature

3. Merge to develop
   # Create PR: feature/my-feature -> develop
   # Review and merge

4. Merge develop to staging
   # Create PR: develop -> staging
   # Test in staging environment

5. Merge staging to master
   # Create PR: staging -> master
   # Deploy to production
```

## Branch Protection Rules (Recommended)

### master
- Require pull request reviews
- Require status checks to pass
- Require branches to be up to date
- Do not allow force pushes
- Do not allow deletions

### staging
- Require pull request reviews
- Require status checks to pass

## Quick Commands

```bash
# Switch branches
git checkout master
git checkout staging
git checkout develop

# Create feature branch
git checkout develop
git pull
git checkout -b feature/feature-name

# Update branch from remote
git checkout <branch>
git pull

# View all branches
git branch -a
```
